# 连续运行流程（1.1.0）

本版落实用户批准的六项优化，并保存首次启动计划。1.0.12删除的限制不恢复；同事检查始终先于简历分析。

## 一次准备，回复1续接

```text
python scripts/quick_start.py --prompt "帮我打招呼，打美康50人"
```

返回plan_file及冻结的企业、岗位、数量、最低分和标题。按pending_startup_actions只执行尚未完成的启动步骤：当前聊天改名、收起侧栏、非CUA打开BOSS、处理已登录提示。实际完成一步后登记：

```text
python scripts/quick_start.py --plan <plan_file> --complete-action set_current_chat_title
```

未出现登录提示也可按实际结果登记该检查已完成；控件不可读记未核验，不把未执行写成成功。回复1前仅等人工选择筛选；不要创建发送运行。用户回复1后：

```text
python scripts/quick_start.py --plan <plan_file> --confirm-filters
```

该命令读取原计划，不再次搜索企业、解释人数或重走启动步骤。重复确认返回同一run_id。显式再传min-score是本次主动修改，省略则保持首次值。相同文字的新任务仍先prepare创建新计划，不按历史文本阻止新任务。

目标：未指定默认150招呼、300查看；只指定招呼数时，查看默认max(300,招呼目标)。因此招呼500默认查看500；明确说查看100则仍按100先到停止，不擅自改用户明确值。

## 一个执行器负责常规步骤

确认筛选并创建运行后，启动悬浮窗，再启动主执行器：

```text
python scripts/launch_progress.py --run <run_id>
python scripts/workflow_runner.py --run <run_id> --hwnd <当前窗口句柄> --launch
python scripts/workflow_runner.py --run <run_id> --status
```

可不传hwnd，由定向UIA查找唯一可用窗口；--no-ocr关闭可选OCR后备路径。正常流程由执行器连续处理，不再让聊天逐条调用record/reserve/resolve/sync/favorite/finish。单步命令保留用于调试、恢复和显式人工操作。

阶段为：选择 → 真正打开并登记本次查看 → 同事检查 → 读取 → 快速触发/完整评估 → 发送核验 → 收藏 → 计时收尾 → 一次写表 → 下一位。

1.1.1起，所有岗位共享每300秒最多10人的招呼窗口。发满才等待余时，慢处理超过300秒不额外等待；跨运行/岗位/重启保留本窗计数。主执行器在send阶段返回rate_limited，自动从原候选人续接，不重复读取/评估；等待时悬浮窗显示剩余秒数，暂停/结束仍有效。单次与三连式都只按首条计人，未知发送占位，同次重试不重复计人。

电子简历采集、OCR和图片/PDF归档失败保留具体原因，写入可见的“运行状态”工作表；尚未评估的失败也保存在账本并在后续/结束导出时呈现。不因可选OCR或归档失败阻止后续候选，不能将失败记为已保存。

打开就绪及下一位切换核验使用ResumePresence，只检查Document及概览控件RuntimeId结构，不采集候选人正文。下一位没有可观察结构信号时改为关闭回列表；同事检查通过后才调用Resume读取。真实页面的无名close-btn支持直接Invoke，避免为了关闭依赖键盘焦点。

主循环统一响应暂停、继续、结束；不恢复每次Invoke前的状态/generation/候选归属或token守卫。每个运行只有一个执行器进程；这是执行归属，不是新的发送授权环节。

运行达到任一数量目标后完成当前记录并结束，不先打开第N+1位。电子简历在可核验的直接后继场景优先使用既有“下一位”箭头，否则返回列表定位；普工只有需要收藏时打开详情，之后回列表。

## 聊天只接管需要判断的部分

执行器状态needs_assessment会返回request_file和response_file。读取request_file中的真实证据，完成现有评分后把评估JSON写到response_file；后台自动从原步骤继续。不要重新打开候选人，也不要重新运行record或增加查看。等待期间执行器不重复采集或解析简历，不反复写相同检查点。

needs_card_visual：查看本次card.png后，写入{state:present/absent,evidence:实际依据}；如果真实图像不可读，写unknown及原因，候选记同事检查待处理，先不评分。普通遮挡时可只读UIA，不截取遮挡图像冒充卡片。

needs_followups只用于用户选了triple：按既有第二、三句话术及实际发送核验执行，写入实际后续句结果后继续；首句已成功仍计成功，不伪造后续结果。single全程不打开聊天小窗追加话术。

needs_attention/needs_page提供实际阶段和原因；先按现行有界技术恢复路径处理，同一执行器从原阶段继续，不另开重复运行。不要把这些内部评估交接变成逐名向用户确认。

## 查看、重试、补写分别记录

candidate-begin --new-visit表示真正重新打开。仅补写record、重复reserve、note、sync或发送重试，均复用本次访问；已完成的查看也可以补写，不增加新行。

同一次未知发送可按现行页面结果重查并重试一次。旧尝试移入message_attempt_history，不再复制候选人的访问和评估行；历史实际发送结果仍可补核，不要求人工核销才能继续。真实重新打开同一个候选人仍可新建访问，不恢复稳定ID历史去重。

执行器在派发前保存“等待核验”阶段，重启后先核验，不盲目重复派发。暂停时保留阶段与材料，恢复不重做已完成的启动动作和本次查看。

## 每人一次写表，文件不变就不重读

report_batch在每人过程中先保留数据库状态，合并record/sync/计时/收藏更新；收尾时只重建一次当日岗位工作簿，再切换下一位。完整评估等待不提前导出，结束快照仍独立生成。

写表失败保留report_written=0与警告，不阻止下一人；后续成功导出会带上此前待补记录。独立单步命令保持即时导出兼容，日常批量路径使用主执行器。

悬浮窗仍每秒刷新，但按文件绝对路径、mtime_ns、大小和文件标识缓存实际行数/绿色行。文件变化、换岗位或跨日使用对应新文件重读；不以数据库成功数冒充已写入的绿色行。

## 美康优先快速触发

同事检查通过后，先读取当前实际UIA正文/经历概览并判断两条直接通道；已经足够命中时不采集完整长图，也不进入旧条件逐项评分。需要时仍可选OCR，无强制前置。

未提供完整评分时，直接通道记录“快速规则分”：基础80，按已知年限扣分（原配置5/10），未知不编造。依据中明确标记direct_rule及真实匹配原文，不冒充完整能力评估；此分数不影响直接触发资格。已有实际评分则保留其基础分及年限扣分口径。

直接通道未命中才交完整评估，旧正常通道仍有效。规则配置version5随新运行冻结；历史快照不回写。

UIA正文和右侧概览分别记录长度。概览未直接命中且正文不足80字时，可选OCR后备路径依据正文字数触发，不因概览较长而漏读图像正文；--no-ocr仍生效，采集失败保留实际概览和警告，不恢复强制截图/OCR门槛。卡片同时识别candidate-card-wrap和card-inner上的has-viewed；姓名可取实际头像的可访问名称，不从未暴露信息猜测。
