# 项目入口、资料与分享

用户正常调用 Skill 时，在 Codex 对话中操作，不启动独立菜单或工作台。先只读运行 `ledger.py runs` 和 `project_registry.py list`，提供：

1. 继续上次项目（显示企业、岗位及运行状态）
2. 查看已有项目
3. 创建新的项目
4. 更新项目
5. 测试
6. 退出

以上六项保持固定编号与原文。在第1项附带显示实际读取的最近企业、岗位和运行状态；无记录时显示“暂无记录”。一次只询问当前必要的信息，不要求用户编辑 JSON 或使用额外界面。

- 继续：读取最近 `run_id`、`profile_path`、企业、岗位与状态。`running`、`paused`、`login_required` 且未超时时沿用账本核验；`expired` 或 `stopped` 时说明结果，并询问是否用同一项目新开运行。未决发送先人工核查，绝不重复点击。正常继续或新开投递不运行环境检测、5 人试投或其他测试，按已授权设置直接开始投递。
- 查看已有项目：以 `project_registry.py list` 的实时结果按 `company` 分组，第一层只列企业编号、企业名称、岗位数与待审核数，用户选择企业后，第二层只列该企业的岗位编号、岗位名称、`project_id` 和审核状态。编号仅用于本轮对话，保留编号到真实路径和项目编号的映射；以完整企业名分组，简称或品牌关系只在资料已有明确对应时作为显示别名，不按关键词合并不同企业。用户已明确企业或岗位时直接定位对应层，名称不唯一时再澄清；不要把所有企业的岗位一次铺开，也不要因企业只有一个岗位就自行启动。
- 选择岗位后：`pending` 岗位只提供查看资料、梳理待确认项和分享草稿，不提供开始投递、不创建运行。`approved` 岗位仍需检查当前文件完整审核条件，再提供开始投递、查看资料、分享或导入；正常投递按已授权设置直接开始。返回企业列表时重新生成相应层的编号映射。
- 新建：依次取得原始资料文件夹、企业、岗位，自动生成岗位项目标识；用户已给出父目录并要求批量整理时，以直接子文件夹作为企业项目分组，按资料识别其独立岗位，不重复索要可从资料得到的信息。原始目录只读；新标准化文件存入 `profiles/<企业>/<岗位>/<企业-岗位-标准化信息.md>`，每个岗位目录单独放置 `project.json`，避免多个岗位共用并覆盖一份元数据。按 [岗位文件格式](profile-format.md) 标注来源、硬条件、加分项、评分依据、冲突和待确认项，忽略原始目录旧的 `*-标准化信息.md` 和派生 `.inspect.ndjson`；多版本差异保留来源，不仅凭文件名或时间裁定事实。
- 更新项目（第4项）：按 [GitHub更新](github-updates.md) 运行 `scripts/skill_update.py update`，每次选择都从update-source.json指定的GitHub仓库检查最新正式Release。有新版时自动下载、校验、备份并安装，显示结果后重新读取更新后的SKILL.md与CHANGELOG.md；没有新版则显示当前和远端版本。无需先选企业或岗位；本地岗位、runtime、账本及运行资料保留。下载失败、校验失败或活动招聘运行阻塞时说明原因，保留当前安装，不启动投递。
- 岗位资料更新（用户明确要求修改企业岗位时）：沿用“查看已有项目”的企业→岗位选择方式；用户已指定目标时直接定位。展示当前资料，取得用户要更新的内容或新资料，只追问无法从材料确定的必要信息。汇总差异后在现有标准化文件中更新并标注来源，保留 `project_id`、`candidate_namespace`、原目录及原始资料；不得新建同名项目来替代更新。筛选条件、评分或话术实质变化时恢复 `pending`，按项目审核流程确认当前完整版本后再设 `approved`；只有非筛选资料备注更新时保留既有审核结论。同步受影响的配置、索引及本 Skill 版本记录。更新操作完成后展示变更摘要和审核状态，不创建投递运行。
- 项目审核：不自行裁定冲突。影响筛选的未决项须在 Codex Plan mode 逐项请用户确认并记录结论；Skill 无法自行切换 Codex 模式。写入确认人和日期后才设 `approval: approved`。条件、评分规则或话术实质变化时恢复 pending。登记后说明当前状态；待审核稿提供查看和梳理问题，完整审核通过后才询问现在投递或稍后处理。
- 测试（第5项）：仅在用户选择此项时运行环境检测、只读预演和最多 5 人的受控试投。实际发送仍需明确授权，并遵守岗位、话术、候选人和账本门禁。测试结束后汇报结果，不自动扩大为完整批次。
- 退出：不执行招聘动作。

`profiles/` 是随 Skill 迁移的项目目录；企业是对话中的项目分组，每个可选择岗位仍对应一份标准化 Markdown、一份独立 `project.json` 和现有格式的 `project_id`，标识仅用小写字母、数字和连字符。`project_registry.py list` 已递归发现岗位文件，无需改变返回格式或账本。保留既有平铺目录/原路径及导入目录兼容，不为分组迁移已登记项目。可参考 [企业岗位索引](../profiles/企业岗位索引.md) 和 [待确认清单](../profiles/待确认清单.md)，但岗位与审核状态始终以实时列表和当前文件为准；索引/清单不带岗位 front matter，不登记成岗位。分享或导入时使用：

```text
python scripts/project_registry.py export --profile <标准化文件> --output <名称.boss-project.zip>
python scripts/project_registry.py import --archive <名称.boss-project.zip>
```

分享包只含 `manifest.json`、`project.json`、岗位 Markdown 和校验信息，不含候选人、简历、简报、账本、登录信息、Cookie、截图或日志。导入时拒绝路径穿越、符号链接、未知格式、校验失败和同名覆盖；只有用户明确确认同名覆盖后才传 `--overwrite`。导入后仍须核对招聘账号与 BOSS 页面岗位。

只有选择“测试”（第5项）时才按 [标准化测试流程](standard-test.md) 运行 `scripts/standard_test.py` 和环境检测；正常投递不以这些测试为前置门槛。便携运行时存在且可用时优先使用包内 `runtime/win-x64/python/python.exe`。
